## 阶段 2 处理核：processor 压缩 / MD5 / 重命名（来源：设计定稿实施阶段 2，处理层）

> 创建于 2026-10-07 00:06

**需求**：单文件处理纯函数——压缩（最长边 ≤1920 等比 + JPEG 质量 80）、输入字节 MD5、统一重命名格式；验收线：`go test` 全绿 + 真实图片体积显著变小（`docs/project/fileforge/archive/2026-10-07-阶段2-处理核-plan.md`）。

**设计定稿**（`docs/project/fileforge/designs-specs.md` §2.2 / §4.4）：

- `Process([]byte)` 纯函数：image.Decode → 超限则 `draw.CatmullRom` 等比缩放 → jpeg.Encode 质量 80；解码失败返回 error（单点隔离由调用方负责）；
- MD5 取**原始输入字节**（判重按原内容，与重编码无关）；`OutName(n)` = `photo_%03d.jpg`（>999 自然增长为 4 位）。

**实施**（TDD：6 个测试先写先红，再实现转绿）：

- `internal/processor/processor_test.go`：大图缩放（2560×1920 q95 渐变 → 1920×1440、压缩比 < 0.6、可再解码）、PNG 转 JPEG（SOI 头）、小图不放大、同内容 MD5 一致且 32 位 hex、三类损坏数据报错、OutName 格式；
- `internal/processor/processor.go`：如上契约实现；
- 途中依赖被 `go mod tidy` 移除过一次（当时尚未 import x/image），`go get` 拉回。

**验证**：`go vet` 通过、`go test -race ./...` 全绿（processor 10.7s）、`go build` 产出 exe。待阶段 3 接入 worker 池后在浏览器做整批闭环验证。

**涉及文件**：`internal/processor/processor.go`、`internal/processor/processor_test.go`、`go.mod`、`go.sum`

## 阶段 3 池化：worker 池 + 进度轮询 + zip 下载（来源：设计定稿实施阶段 3 = 验收底线，全栈）

> 创建于 2026-10-07 00:26

**需求**：并发数可调，整批「上传 → 处理 → 下载 zip」闭环可演示；进度先轮询（阶段 4 升级 SSE）。

**设计定稿**（`docs/project/fileforge/designs-specs.md` §2.2，增量注记 261007 条目）：

- worker 池：带缓冲 channel 分发 `*FileItem`，N=并发数，WaitGroup 收尾后 `task.Finish(elapsed)`；
- 单文件序：读盘 → `MD5Hex` 判重（Run 内局部 map+mutex，先到先得，**命中即跳过压缩**）→ `Process` → outputs/photo_NNN.jpg（完成序，atomic 发号，重复/失败不占号）→ `task.Lock()` 下更新 FileItem；
- 上传即开跑：POST /api/tasks 后 service 异步 RunByID，无独立「开始处理」键（与设计全记录 §4.3 一致）。

**实施**（TDD：先写 11 个失败测试再实现）：

- processor `MD5Hex`、store `GetRef`、service `Run/RunByID/processOne/DoneFiles`、handler `download`（zip 流式，只含 done 文件）；
- 前端：总进度条 + 三种结局统计 + 完成后「下载结果 zip」按钮，1s 轮询；
- 修复一个测试偶发：Windows 下 `t.TempDir` 清理与在途 worker 竞争 → 上传类测试统一等任务 done。

**验证**：`go vet` + `go test -race -count=1` 全绿（34 个测试）；浏览器整批实测：4 文件（2 独立大图 + 1 重复 + 1 损坏）→ 4/4 完成、总耗时 0.6s、压缩 1.27MB→538KB、判重命中、损坏单点隔离（报 unexpected EOF）；zip 解包核验恰含 2 个 1920×1440 JPEG。排障记录：一度全卡「待处理」——根因是 8080 上还挂着旧版 exe（bind 失败被我忽略），换新构建即恢复；教训：启动脚本要校验 bind 是否成功。

**涉及文件**：`internal/processor/processor.go(+test)`、`internal/store/store.go`、`internal/service/service.go(+test)`、`internal/handler/task.go(+test)`、`web/index.html`、`web/app.js`、`main.go`

## 阶段 4 实时推送 + 压缩程度可选（来源：设计定稿实施阶段 4 + 开发者新需求 design v0.2，全栈）

> 创建于 2026-10-07 00:41

**需求**：① 进度条无刷新实时跳动（SSE，轮询为降级备份，阶段 4 验收标准）；② 开发者口述新需求「自己选择压缩的程度」——落为 design.md **v0.2 草案（待开发者审核）**：压缩质量滑块 50~95 步进 5 默认 80，最长边 1920 规则不变。

**设计定稿**（`docs/project/fileforge/designs-specs.md` 增量注记 261007 阶段 4 条目）：

- SSE：service 每任务订阅者集合，文件终结推 `{done,total,last}`、收尾推 `final:true`；订阅时任务已 done 立即补发 final（覆盖小任务快过建连的竞态窗口）；
- 质量：`Process(data, quality)`，handler 钳位 50~95 缺省 80，processor 兜底 1~100。

**实施**（TDD：新增/更新 14 个测试先红后绿）：

- store 加 `Quality`；processor 质量入参 + 质量影响体积测试；service 广播器（Subscribe/notify/closeSubs）；handler `events` SSE 端点 + quality 钳位 + JSON 字段；
- 前端：压缩质量滑块（含「低→更小 / 高→更清晰」提示）、EventSource 优先 + onerror 降级轮询 + final 后全量拉取修正终态。

**验证**：`go vet` + `go test -race -count=1` 全绿（41 个测试）；浏览器实测：质量 50 下同批图完成 4/4（总耗时 0.5s），**同图 q50=358.6KB vs 此前 q80=538KB**（质量直接控制体积）；网络面板仅 1 条 `/events` 长连接 + 1 次收尾全量拉取（未触发轮询降级），控制台干净。

**涉及文件**：`internal/store/store.go`、`internal/processor/processor.go(+test)`、`internal/service/service.go(+test)`、`internal/handler/task.go(+test)`、`web/index.html`、`web/app.js`、`docs/project/fileforge/design.md`（v0.2 草案）

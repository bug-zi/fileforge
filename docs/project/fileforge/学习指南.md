## 一、项目框架总览

### 1.1 一句话定位

完全本地运行的批量图片处理工具：Go + Gin，全功能打包单个 exe（前端 go:embed 嵌入），运行零外部依赖。核心卖点：同一批图并发 1 vs 32 的耗时对比。

### 1.2 依赖结构（自上而下，严格单向）

```
main.go   装配 + 启动 + 优雅停机 + go:embed 静态页
   └─▶ internal/handler    HTTP 层：multipart 上传 / SSE 进度 / zip 下载 / 路由钳位
          └─▶ internal/service   任务生命周期：建任务 → channel → worker 池 → 汇总 → SSE 广播
                 ├─▶ internal/processor   纯函数：解码 → 缩放 → 重编码 / MD5 / 命名
                 └─▶ internal/store       内存任务表：Mutex + map + atomic
web/   原生 JS 单页（编译期嵌入）
```

| 文件 | 行数级 | 职责 | 类比 |
|---|---|---|---|
| `internal/processor/processor.go` | ~92 | 单张图片处理纯函数 | 车间机器 |
| `internal/store/store.go` | ~161 | 内存任务表（锁 + map + 快照） | 账本 |
| `internal/service/service.go` | ~446 | 任务生命周期 + worker 池 + 发布订阅 | 调度员 |
| `internal/handler/task.go` | ~310 | HTTP 接口与协议细节 | 前台接待 |
| `main.go` | ~64 | 装配、嵌入、优雅停机 | 总开关 |

### 1.3 核心数据流（必背主线）

1. 浏览器 multipart 上传 → `POST /api/tasks` → `handler.createTask`（task.go:45）
2. `service.CreateTask`（service.go:38）：生成随机任务 ID、文件流式落盘 `uploads/{taskID}/`、以 `ready` 状态入 store
3. （可选预览）`GET /api/tasks/:id/estimate` → `service.Estimate`（service.go:112）用第二个小池子按指定质量真编码一遍 → 返回精确输出大小
4. （开始）`POST /api/tasks/:id/start` → `handler.startTask`（task.go:67）起 goroutine → `service.Run`（service.go:270）
5. Run：jobs channel（缓冲 = 文件数）→ N 个 worker（N = 用户并发数）→ `processOne`：读文件 → MD5 判重 → `processor.Process` → 写 `outputs/{dirName}/photo_NNN.jpg` → 持 Task 锁更新 FileItem
6. 每个文件终结：atomic 计数 +1 → `notify` 向 SSE 订阅者广播一帧
7. 全部完成：`task.Finish` → 广播 final 帧 → `closeSubs` 关闭订阅
8. `GET /api/tasks/:id/download` → `zip.NewWriter(c.Writer)` 流式打包（task.go:174）
9. `GET /api/history` → 内存历史表（重启即清，有意设计）

### 1.4 有意的设计决策（每个都能讲出「为什么」才算掌握）

| 决策 | 理由 | 代价（要能主动说出） |
|---|---|---|
| 任务不持久化，重启即清 | 工具型单机场景，零数据库零依赖 | 关进程丢历史 |
| PNG 统一转 JPEG | 输出规格统一 + 体积最优 | 丢透明通道、截图文字轻微毛边 |
| 单文件失败不中断整批 | recover + error 双重隔离，鲁棒 | 失败文件不进 zip（需单独提示用户） |
| SSE 丢帧策略（service.go:243-246） | 慢订阅者不拖垮广播 | 订阅方可能漏中间帧，靠 final 帧兜底 |
| 判重 MD5 在解码前（processor.go:40） | 重复文件跳过全部昂贵处理 | — |
| 无前端框架、无构建工具 | 保持单 exe、简单 | 手写原生 JS |
| EXIF 方向未处理 | 已知限制，文档明示 | 竖拍照片可能横着出来 |

## 三、分站详解

### 第 0 站：Go 语言地基（前置）

**目标**：打开 processor.go 逐行读，不因语法卡壳。
**方法**：以项目 5 个 Go 文件当「例句库」，遇到不懂的语法回来定位，交给交互 AI 讲解。清单：

- 包与导入；空导入 `_ "image/png"` 的含义（processor.go:10，第 1 站展开）
- 函数多返回值 + `if err != nil` 惯例（processor.go:33-44）
- struct 定义与字面量（store.go:21-30 的 FileItem 是干净范例）
- 指针：`*Result` 返回值、`&out` 取地址（processor.go:33, 50）
- slice 与 map 基本操作（store.go:109、service.go:275）
- `defer`（store.go:118）
- fmt 动词：`%d` `%03d` `%s` `%w`（processor.go:44, 91）
- 字符串与 []byte 互转

**过关**：能把 processor.go 全文逐行口述大意。

### 第 1 站：processor —— 纯函数层

**必读**：`internal/processor/processor.go` 全文 + `processor_test.go`。

**知识点**：
1. 纯函数定义：不碰共享状态 → 天然并发安全（第 3 站的伏笔，16 个 worker 同时调它也不会竞态）
2. `(*Result, error)` 双返回范式；`%w` 错误包装 vs 字符串拼接（processor.go:33-44）
3. 质量钳位兜底：handler 已钳位，最底层仍不信任输入（processor.go:34-39）——分层校验思想
4. `image.Decode` 注册制解码器；空导入 `_` 执行 init（processor.go:8-10, 42）
5. 接口的日常：读用 `bytes.NewReader`（实现 io.Reader），写用 `bytes.Buffer`（实现 io.Writer）（processor.go:42, 49-52）
6. JPEG 有损压缩：quality 1~100 = 有损程度旋钮；这是「精确压缩预览」功能的理论基础（processor.go:50）
7. 等比缩放数学：float64 防整数除法截断；先乘后除（processor.go:76-83）
8. `draw.CatmullRom` 插值算法——全项目唯一第三方依赖的存在理由（processor.go:85）
9. MD5 + hex（processor.go:64-67）；判重顺序 = 性能（processor.go:40）
10. `%03d` 补零命名保证字典序 = 序号序（processor.go:90-92）

**自测题**：
1. MD5 为什么在 `image.Decode` 之前算？反过来代价是什么？
2. 删掉 `_ "image/png"`，编译能过吗？运行时什么现象？
3. 若缩放误写成 `nh = h / w * MaxEdge`（先除后乘），4000×3000 的图 nh 是多少？后果？
4. 为什么说 Process 是并发安全的？它的前提是什么？
5. quality 传 0 或 150 分别会怎样？有哪两层在钳位？

**实验**：
- `go test ./internal/processor/ -v`，对照测试理解纯函数怎么测
- 同一张图分别用 quality 10 / 50 / 95 编码，记录体积，画出「质量-体积」感受曲线
- 把 `draw.CatmullRom` 换成 `draw.NearestNeighbor`，对比缩图画质（改完记得恢复）

### 第 2 站：store —— 第一把锁与快照

**必读**：`internal/store/store.go` 全文 + `store_test.go`（重点 `TestConcurrentAccess`，store_test.go:122）。

**知识点**：
1. 竞态条件：Go 的 map 并发读写会直接 fatal（不是数据错，是进程崩）——为什么需要锁
2. `sync.Mutex` 与 `defer Unlock` 惯例（store.go:116-120）
3. 双层锁：`Store.mu` 保护 tasks map（store.go:107-110），`Task.mu` 保护单任务可变字段（store.go:52-55）；`GetTask` 先后拿两把（store.go:122-132）
4. `atomic.Int64` 做完成计数（store.go:52-62）——为什么 done 用 atomic 而其他字段用 mu：**单变量无临界区 vs 复合状态需一致快照**（这是全项目最重要的并发设计辨析，第 3 站的 seen+seenMu 是对照组）
5. 快照模式：`Snapshot` 返回值拷贝（store.go:89-105）；`TaskView`（读方）vs `*Task`（写方经 GetRef，store.go:136-140）——避免读方持引用看到半写状态
6. 状态常量：文件五态 + 任务三态（store.go:9-19）

**自测题**：
1. 不加锁并发写 map 会发生什么？（最好亲手见过一次）
2. `GetTask` 若返回 `*Task` 而不是快照，会出什么问题？
3. done 和 Status 的保护机制互换一下行不行？为什么？
4. `ListHistory` 循环体内为什么还要拿 `t.mu`（store.go:142-160）？

**实验**：
- `go test -race ./internal/store/ -v`
- 手写 20 行小程序：10 个 goroutine 并发写同一个 map，先不加锁跑 `-race` 看报错，加锁后变绿——**亲眼看一次竞态**

### 第 3 站：service —— worker 池并发核心（答辩主战场）

**必读**：`internal/service/service.go` 的 Run（:270-302）、processOne（:304-364）、finishItem/failItem（:367-392）、Estimate（:112-164）、Subscribe/notify/closeSubs（:212-260）、saveFile/sanitizeName（:395-437）。

**知识点**：
1. goroutine：`go func()` 的轻量与廉价（service.go:283）
2. channel 三要素：带缓冲 `make(chan *FileItem, len(task.Files))`（service.go:280）、`close(jobs)` 的广播语义（service.go:293）、`for range ch` 消费到关闭（service.go:285）
3. **worker 池模式**（全项目灵魂）：池大小 = 用户并发数（service.go:281-289）；生产者（主 goroutine 填 jobs，service.go:290-292）→ N worker 扇出 → `wg.Wait()` 汇聚
4. `sync.WaitGroup`：Add/Done/Wait 严格配对（service.go:281-294）；想想 Add 放循环外还是内、为什么
5. atomic 与 Mutex 的适用边界（对照第 2 站）：输出发号 `seq.Add(1)`（service.go:346）用 atomic；判重集合 `seen` 是复合「查+写」必须 `seenMu`（service.go:274-275, 325-330）
6. recover 单文件隔离：一个 panic 只废一个文件（service.go:311-315）
7. 两个池的参数哲学：Run 用用户并发数、Estimate 用 NumCPU 上限 8（service.go:129-135）——为什么策略不同
8. 发布订阅：Subscribe 返回**只读** channel（service.go:212）、notify 非阻塞发送 + 丢帧（service.go:239-248）、closeSubs 收尾关闭
9. `map[chan []byte]struct{}`：空结构体当集合用，零内存（service.go:219-226）
10. 安全：`sanitizeName` 剥路径成分防目录穿越（service.go:427-437）；同名文件加序号防覆盖（service.go:395-425）

**自测题**：
1. jobs 缓冲设为 `len(task.Files)` 意味着什么？改成无缓冲（`make(chan *FileItem)`）行为差在哪？
2. 忘记 `close(jobs)` 会发生什么？谁在等谁？
3. worker 里若没有 recover，一张图触发 panic 整批会怎样？
4. `seen` 为什么必须配 Mutex？能不能也用 atomic？反过来 `seq` 为什么不必用锁？
5. `notify` 用 `select + default` 丢帧而不是阻塞发送——如果阻塞，一个断网僵死的 SSE 客户端会拖垮什么？
6. Estimate 池上限取 8 而不是 32，可能的考虑是什么？
7. `closeSubs` 为什么要持 `subMu`？和 notify 的锁是什么关系？

**实验**：
- **亲手做答辩杀手锏**：同一批 16 张大图，并发 1 跑一轮、并发 32 跑一轮，从历史表抄下两组耗时——这两个数字答辩时要现场讲
- 给 processOne 加一行打印（worker 编号 + 文件名），观察文件在 worker 间怎么被瓜分（看完删掉）
- 把 service.go:280 改成无缓冲并注释掉 worker 循环，运行观察 `all goroutines are asleep - deadlock!`，体会 channel 阻塞与收尾配对；然后恢复
- `go test -race ./...` 全绿

### 第 4 站：handler —— HTTP / SSE / 流式 zip

**必读**：`internal/handler/task.go` 全文。

**知识点**：
1. HTTP 基础：方法、路径参数、状态码语义（task.go:35-42 路由表；400 参数错 / 404 不存在 / 409 状态冲突）
2. Gin：`c.Param` / `c.PostForm` / `c.Query` / `c.JSON`（task.go:45 起）
3. multipart 上传：`c.MultipartForm`、`form.File["files[]"]`（task.go:46-51）——浏览器怎么把多文件装进一个请求
4. 入口钳位：`clampConcurrency` / `clampQuality`（task.go:219-245）——对外输入的第一道闸，与 processor 兜底构成两层
5. **异步任务模式**：`go func(){ RunByID }()` 后立即返回 200（task.go:78）——为什么不能同步跑完再返回（请求超时、连接挂死、体验）
6. **SSE**：三个响应头（task.go:122-123）、帧格式 `data: ...\n\n` 与 `event: complete`、`Flush` 推送（task.go:130-139）、`c.Request.Context().Done()` 感知客户端断开（task.go:150）、连接前任务已完成则直接补发 final（task.go:142-146）
7. SSE vs WebSocket vs 轮询：为什么单向进度选 SSE（原生重连、实现简单），断线降级轮询兜底
8. **流式 zip**：`zip.NewWriter(c.Writer)` + `io.Copy` 边读边发（task.go:185-198）——对比「先打完整包再返回」的内存/磁盘/首字节延迟差异
9. struct tag 控制 JSON 字段名（task.go:247-266）

**自测题**：
1. startTask 若同步执行完再返回，大批图片时客户端会遇到什么？
2. SSE 三个响应头各管什么？不 Flush 会怎样？
3. zip 下载若先在内存拼完整个包，500 张 5MB 图会怎样？
4. estimate 在任务已开始时返回 409 而不是 400，语义差别是什么？
5. 客户端中途关掉页面，events 这个连接的服务端代码从哪里感知到、怎么退出循环？

**实验**：
- 跑任务的同时 `curl -N http://localhost:8080/api/tasks/<id>/events`，亲眼看 SSE 原始帧流
- 浏览器 F12 网络面板观察 start 请求「立即返回」与 events 长连接并存

### 第 5 站：main —— 装配、go:embed、优雅停机

**必读**：`main.go` 全文（仅 64 行，逐行精读）。

**知识点**：
1. 依赖注入式装配：`store.New()` → `service.New(st, ...)` → `handler.New(svc)`（main.go:26-28）——为什么不用全局变量（可测试、依赖方向显性化）
2. `go:embed`：编译期把 web/ 塞进 exe（main.go:22-23）；`fs.Sub` 取子目录（main.go:30）；`http.FS` 适配给静态服务（main.go:41）——「单 exe 零依赖」的技术实现
3. `http.Server` 与 `ListenAndServe` 放进 goroutine（main.go:43-54）；`errors.Is(err, http.ErrServerClosed)` 区分正常关停与真错误（main.go:51）
4. **优雅停机**：`signal.NotifyContext` 捕获 SIGINT/SIGTERM（main.go:46）、主协程阻塞在 `<-ctx.Done()`（main.go:56）、`srv.Shutdown` 停新连接等旧请求 + 10s 超时强退（main.go:58-62）
5. 这个「goroutine 跑服务 + 主协程等信号 + Shutdown」是 Go 后端通用骨架，值得背下来

**自测题**：
1. 删掉 `<-ctx.Done()` 这行，程序启动后立刻发生什么？
2. Shutdown 调用后，新请求和正在处理的旧请求分别什么命运？
3. web/ 下改了 index.html，exe 会变吗？要做什么才行？这体现了 go:embed 的什么特性？
4. main 里三个组件的构造顺序能打乱吗？说明了什么依赖方向？

**实验**：
- 任务跑到一半 Ctrl+C，观察「收到退出信号，等待在途请求完成…」日志与最终退出
- `go build -o fileforge.exe .`，把 exe 单独拷到别的目录运行——验证「单文件零依赖」不是口号

### 选学：测试与前端

- 各层 `*_test.go`：看测试怎么反推设计（如 store_test.go 的 `TestSnapshotIsCopy` 印证快照模式）
- `web/app.js`：`EventSource` 订阅 SSE、失败降级轮询——学 Go 为主时略读即可

## 五、交给交互 AI 的使用说明

**开始某站（粘贴给交互 AI）**：

> 我在学 Go 项目 fileforge（仓库在本地，工作目录即仓库根）。请先读 `docs/project/fileforge/学习指南.md` 的第 N 站，按该站带我学习：以指南列的文件与行号锚点为准逐段带读源码，讲清「是什么、为什么这么设计、不用它会怎样」。我的 Go 水平：刚入门。规则：一次只讲一个知识点块，讲完用该站自测题考我，我回复后再继续；所有结论必须给出 file:line 证据。

**结束某站（验收）**：

> 请对 fileforge 学习指南第 N 站做模拟答辩：围绕该站知识点连续追问（含「为什么不用 X 代替 Y」类问题），暴露我讲不清的点；最后给出掌握度评估与需要回炉的清单。我会把复述记录写进 `docs/project/学习报告框架.md`。

**节奏建议**：每站按「读码 → 自测问答 → 动手实验 → 费曼复述（你讲、AI 挑错）」循环；第 3 站体量最大，可拆成「channel 与池」「判重与隔离」「发布订阅」三小节。

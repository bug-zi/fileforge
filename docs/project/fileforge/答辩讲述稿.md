## 一、痛点开场（约 30 秒）

批量压缩图片人人需要，但现在的工具都有硬伤：在线网站要传隐私照片、有广告和限制；微信压缩不可控；桌面软件捆全家桶；命令行对普通人太难。

（一句话亮牌）所以我做了 FileForge——**文件不出自己的电脑、双击就用、一次管够**：批量压缩，顺带解决重复文件和命名混乱。

## 二、演示剧本（约 3 分钟）

准备：一个文件夹，约 16 张大图 + 2 张内容完全相同的图 + 1 张损坏假图。

1. 双击 exe，终端显示「FileForge 已启动，请打开 http://localhost:8080」；
2. 浏览器打开页面，把文件夹拖进拖拽区——文件列表逐行显示文件名和大小；
3. **并发数拨到 1**，跑完一轮，指着历史耗时对比表第一行「记住这个时间」；
4. 同一批文件，**并发数拨到 32**，再跑一轮——历史表两行并排，时间差就是 goroutine 并发的收益（杀手锏，停顿让评委看数字）；
5. 指着文件列表讲三种结局：
   - 完成（显示 原大小 → 压缩后）；
   - 重复（MD5 相同，不进结果包）；
   - 失败（损坏图无法解码，但**没有影响整批**）;
6. 点「下载结果 zip」，解压验证：图片可打开、体积变小、命名是 photo_001.jpg 序列；损坏与重复的不在包内；
7. 收尾 30 秒：SSE 实时进度（进度条自己走）、质量滑块现场改压缩程度、go:embed 单文件零依赖。

## 三、技术点讲解（每个 1 分钟，按评委追问挑着讲）

| 技术点 | 讲法 |
|---|---|
| goroutine + channel 任务分发 | 每个文件包成一个 job 写进带缓冲 channel；启动 N 个 worker `for job := range ch` 消费——N 就是滑块那个数，调并发就是调池大小 |
| 并发收益量化 | 历史耗时对比表：同一批文件并发 1 vs 32，两行数字并排；原因：压缩是 CPU 密集，多核并行瓜分 |
| sync 原语各就各位 | `WaitGroup` 等 worker 收工、`atomic` 做完成计数和输出发号、`Mutex` 保护任务表和判重集合——为什么计数用 atomic 而不是 mutex（无临界区、单变量） |
| SSE 实时推送 | 每完成一个文件立即推 `{done, total, last}`，进度条无刷新自走；断线自动降级轮询——**永不比现在更差**（设计兜底） |
| go:embed | 前端两个文件编译期嵌进 exe，Docker CLI 同款做法，双击即用零依赖 |
| HTTP 文件处理 | multipart 流式上传（不占大内存）、`archive/zip` 流式下载（不落临时包） |
| 错误隔离 | worker 内 `recover` + err 捕获，单图损坏只标记该文件，整批继续——「单点失败不拖垮全局」 |

## 四、追问预案

- **为什么不做持久化？** 工具型单机场景，任务生命周期 = 页面会话；重启即清是有意取舍，换来零数据库、零依赖（非目标里写明了，答辩主动讲）。
- **为什么 PNG 转 JPEG？** 换规格统一（输出全是 photo_NNN.jpg）+ 体积最优；代价是截图文字轻微毛边，当场可以展示对比。
- **判重为什么先算 MD5 再压缩？** 重复文件直接跳过压缩省 CPU；MD5 只哈希原始字节，和重编码无关。
- **并发开 32 会怎样？** 任务里有互斥的判重集合和任务锁，粒度都很小，实测扩展良好；CPU 密集型任务太多线程会互相挤占，32 是滑块上限不是推荐值。
- **内存为什么这样设计（快照读）？** 读方拿值拷贝快照，写方（worker）持每任务锁——避免读到半写状态，`go test -race` 全绿是证据。
- **EXIF 旋转为什么没做？** 已知限制，写在文档里；有余力时的扩展方向（解码后按 EXIF 旋转再编码）。
- **安全上做了什么？** 上传文件名剥离路径成分防目录穿越；同名文件自动加序号防覆盖。

# FileForge（文件工坊）设计文档

> 日期：2026-10-06
> 状态：设计定稿，待开发者审核
> 项目性质：Go 语言学习验收项目（3 周学习成果验收，截止 2026-10-11 前后）
> 验收形式：现场演示能跑 + 文档与答辩

## 1. 背景与痛点

图片批量处理是高频刚需，但现有工具各有硬伤：

- **在线压缩网站**：照片要上传到陌生服务器（隐私风险），常有数量/大小限制、广告、注册门槛；
- **微信/QQ 传输压缩**：压缩率不可控，画质损失不可知；
- **桌面工具软件**：捆绑全家桶、广告；
- **命令行工具（ImageMagick）**：对普通用户有技术门槛。

**痛点一句话**：批量压缩图片，要么牺牲隐私，要么忍受广告限制，要么有技术门槛——缺一个「文件不出自己电脑、双击就用、一次管够」的工具。

**本项目定位**：完全本地运行的批量图片处理工具——单文件 exe、零外部依赖、拖进来就压，同时解决重复文件（MD5 去重）与文件名混乱（统一重命名）两个搭车痛点。

## 2. 目标与非目标

### 目标（5 天内交付）

1. 浏览器拖入一批图片（jpg/png，可 200+ 张），批量处理；
2. 处理流水线：等比压缩（最长边 ≤1920 + JPEG 质量 80）、MD5 去重、统一重命名（`photo_001.jpg` 序列）；
3. 处理进度**实时**显示（SSE 推送，进度条无刷新自走）；
4. **并发数可调**（1~32 滑块），并保存每次任务耗时形成历史对比表——演示 goroutine 并发收益的核心载体；
5. 完成后一键打包 zip 下载；
6. 全部功能打包进**单个 exe**（前端经 go:embed 嵌入），双击即用。

### 非目标（明确不做）

- 不做视频处理、水印、格式批量转换（未来可扩展）；
- 不做多用户/登录/权限；
- 不做任务持久化——任务存内存，重启即清（有意的设计决策，答辩可讲）；
- 不引入前端框架与构建工具——原生 HTML + JS 单页。

## 3. 演示剧本（验收当天的操作脚本）

**准备**：测试文件夹约 200 张图片，故意混入 2 张内容完全相同的图 + 1 张损坏的假图。

1. 双击 exe，终端显示 `FileForge 已启动，请打开 http://localhost:8080`；
2. 浏览器打开页面，将文件夹拖入拖拽区，文件列表逐行显示（文件名 + 大小）；
3. 并发数拨到 **1**，点「开始处理」，跑完记录耗时（约 38s），「记住这个时间」；
4. 同一批文件，并发数拨到 **16**，再跑一次（约 4s）——**历史耗时对比表两行数字并排**，此为答辩杀手锏；
5. 指着文件列表讲三种结局：完成（压缩率）、重复（MD5 相同，不进 zip）、失败（无法解码，单点失败不影响整批）；
6. 点「下载结果 zip」，解压验证：图片可打开、体积变小、命名规整；损坏与重复的不在包内但报告中有记录；
7. 收尾 30 秒：SSE 实时推送（复用 Feed 系统所学）、go:embed 单二进制零依赖。

**页面布局（五块）**：拖拽区 / 并发数滑块 / 文件状态列表 / 总进度条 + 下载按钮 / 历史耗时对比表。

## 4. 技术方案

### 4.1 技术栈与依赖

- Go 1.22+，Gin（HTTP 框架，与所学一致）；
- 第三方依赖仅 1 个：`golang.org/x/image/draw`（高质量缩放），编译期引入，运行时零外部服务；
- 图片编解码用标准库 `image/jpeg`、`image/png`；
- zip 打包用标准库 `archive/zip`（流式）；
- 数据存储：内存（`sync.Mutex` 保护的 map），无数据库。

### 4.2 目录结构

```
fileforge/
├── main.go              // 入口：装配 + 启动 HTTP 服务
├── internal/
│   ├── handler/         // HTTP 接口：上传 / SSE 进度 / zip 下载 / 静态页
│   ├── service/         // 任务生命周期：建任务、分发 job、汇总结果
│   ├── processor/       // 单文件处理（纯函数）：压缩、MD5、重命名
│   └── store/           // 内存任务表（mutex + map）
├── web/                 // index.html + app.js（go:embed 嵌入二进制）
├── docs/specs/          // 本文档
└── go.mod
```

### 4.3 核心数据流

```
浏览器拖文件
  → POST /api/tasks（multipart 上传，文件存临时目录 uploads/{taskID}/）
  → service：每个文件包成一个 job，写入带缓冲 channel（任务队列）
  → N 个 goroutine worker 从 channel 取 job 执行（N = 并发数滑块值）
      worker 内：MD5 计算 → 压缩流水线（见 4.4）→ 输出到 outputs/{taskID}/
      每完成一个：原子计数 +1 → SSE 广播进度
  → 全部完成：任务标记 done，记录总耗时
  → GET /api/tasks/{id}/download：archive/zip 流式打包 outputs 目录返回
```

API 一览：

| 方法与路径 | 作用 |
|---|---|
| `GET /` | 返回嵌入的单页前端 |
| `POST /api/tasks` | multipart 上传文件 + 并发数参数，创建任务 |
| `GET /api/tasks/{id}` | 轮询任务状态（SSE 的降级备份） |
| `GET /api/tasks/{id}/events` | SSE 进度推送 |
| `GET /api/tasks/{id}/download` | zip 流式下载处理结果 |
| `GET /api/history` | 历史任务耗时对比 |

### 4.4 压缩流水线（processor 层，纯函数）

```
文件字节 → ① image.Decode 解码为像素矩阵
         → ② 最长边 > 1920 则等比缩放（draw.CatmullRom）
         → ③ jpeg.Encode 重编码，质量 80
         → 输出字节
```

- 体积收益来自两个乘法：像素总量约降至 1/4（缩放）+ 重编码省 20~40%（质量 90+ → 80）；
- PNG 统一转 JPEG 输出（取舍：截图文字边缘轻微毛边，换规格统一与体积最优）；
- 非图片/损坏文件：解码失败 → 标记「失败 + 原因」，仅做 MD5 与原样归档，不影响整批；
- 已知限制（答辩可主动讲）：EXIF 方向信息未处理，手机竖拍照片可能方向错误——有余力则加 EXIF 校正。

### 4.5 并发模型（答辩核心）

- 任务队列：带缓冲 channel，job 为 `{taskID, 文件路径}` 结构；
- worker 池：启动 N 个 goroutine，`for job := range ch` 消费；N 由创建任务时的参数决定；
- 进度计数：`atomic.Int64` 完成数，SSE 每次变更推送 `{done, total, 当前文件状态}`;
- 收尾：`sync.WaitGroup` 等待全部 worker 退出后标记任务完成；
- 错误隔离：worker 内 recover + err 捕获，单文件失败仅记录该文件状态。

### 4.6 优雅停机（加分项，复用 Feed 系统链路 1 改造所学）

`signal.NotifyContext` + `http.Server.Shutdown`：收到 SIGINT/SIGTERM 后停止接新任务、等正在处理的文件做完、再退出。

## 5. 错误处理与测试

- 错误策略：单文件失败不中断整批，结果列表逐文件展示状态（完成/重复/失败+原因）；
- 重复判定：MD5 相同 → 保留首个，其余标「重复」，不进 zip；
- 单元测试（`go test ./...`）：
  - processor：真实测试图压缩后体积变小、最长边 ≤1920；两份相同内容文件 MD5 判重命中；损坏文件返回错误；
  - store：并发读写任务表无竞态（`go test -race`）；
- 落地判定：`go vet ./...` + `go test ./...` 全绿 + `go build` 产出可运行 exe。

## 6. 实施阶段（阶段 + 验收标准；阶段 3 完成即达验收底线）

| 阶段 | 内容 | 验收标准 |

| 1 骨架 | 项目初始化 + 上传→存盘→文件列表 | 浏览器拖文件，服务端收得到、列表列得出 |

**风险兜底**：进度推送可随时退化为轮询；演示前一天完整录屏备份；exe 与测试图片包提前准备，现场不编译、不联网装任何东西。

## 7. 答辩技术点清单（弹药库）

| 技术点 | 在项目中的体现 |
|---|---|
| goroutine + channel 任务分发 | worker 池消费任务队列，并发数即池大小 |
| 并发收益量化 | 历史耗时对比表：并发 1 vs 16，现场数字对比 |
| sync 原语 | WaitGroup 收尾、atomic 计数、Mutex 保护任务表 |
| SSE 实时推送 | 进度条无刷新自走（复用 Feed 系统所学） |
| go:embed | 前端嵌进单二进制，Docker CLI 同款做法 |
| HTTP 文件处理 | multipart 上传、流式 zip 下载 |
| 有意的设计取舍 | 不持久化（内存任务）、PNG 转 JPEG、单点失败不中断整批 |
| 优雅停机（加分） | signal.NotifyContext + Server.Shutdown |
